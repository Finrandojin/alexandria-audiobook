## A — Stale audio scored as fresh

`tts.py` has **26 `return False` sites**. **Zero of six** experiment harnesses
checked that boolean; all tested `os.path.exists(wav)` instead. With a WAV left
at that path by an earlier run, a *failed* generation was counted as a success
and stale audio was scored as fresh. Invisible to the harness, artifact looks
complete, number wrong in a direction nobody checks.

Fixed with **one shared renderer**, not six patches — six independent copies is
precisely how six of them came to share the bug. `experiments/generation.py`
deletes the output *first*, dispatches through `voice_category` as production
does, checks the boolean, checks the file is non-empty, and **raises**. A caller
forgetting to check a returned bool is how this started; an exception cannot be
ignored by omission.

`ok is False`, not `not ok` — some paths return `None` on success, and treating
that as failure would discard good audio.

`nonprose_split_test` needed more than a swap: that comparison is *paired*, so a
failure now drops the segment from **both** arms and records it. Letting the
surviving arm through is exactly finding 5's asymmetry.

**Still open:** `clone_vs_lora.py` and `voice_data_saturation.py` have the same
pattern. Flagged rather than silently widening scope; they were not part of this
week's runs.

## B — Finding 4, from mitigated to fixed

The review's closing note was right: the intervening-name rule required a
caller-supplied roster, so with no roster the original false attribution simply
returned. A rule that only works when the caller already knows the answer is
barely a rule.

Capitalised, non-sentence-initial tokens that are neither the target nor a
common capitalised non-word are now treated as intervening characters.

```
gender_from_narration("Subaru watched Emilia raise her hand." * 3, "Subaru")
  before:  ('female',  'medium', 0 masc / 3 fem)
  after:   ('unknown', 'unknown', 0 / 0)

same text, "Emilia"  ->  ('female', 'medium', 0 / 3)     # true referent kept
```

The guess is **asymmetric on purpose**. A place name wrongly blocked costs one
piece of evidence out of hundreds; a character name wrongly missed costs a
character the wrong voice.

**Verified on real data rather than assumed** — over-blocking would have been a
silent regression. Across 180,974 characters of narration:

| character | with roster | roster-free |
| --- | --- | --- |
| SUBARU | male, 83/10 | male, **88**/10 |
| EMILIA | female, 0/9 | female, 0/9 |
| REINHARD | male, 14/1 | male, 14/1 |
| ROM | male, 9/0 | male, 9/0 |
| SATELLA | female, 3/12 | female, 3/12 |
| FELT | unknown, 9/14 | unknown, 9/14 |

Every verdict agrees. No evidence lost.

The module remains **NOT WIRED INTO PRODUCTION**. That has not changed and is
still a product decision rather than a defect fix.

## E — The training OOM, re-diagnosed

Earlier today I attributed the first distill-training death to a concurrent
`llama-server` stealing VRAM, and cited it as the cost of the `gpu_job.sh` race.

The second attempt died at **step 218/1250, the same step**, with the GPU
otherwise idle, 14.72 GiB free, on a 1.13 GiB request. Same step twice with
memory available is fragmentation, not contention.

The lock race was real and worth fixing. **It was not the cause of this OOM,**
and saying it was is the kind of mechanism-without-reproduction the review
called out.

Now running with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` (the remedy
the error message itself names), `--save_steps 100`, and a retry policy decided
once and applied identically on every attempt: on non-zero exit, resume from the
latest checkpoint if one exists, otherwise stop. Previously `save_strategy` was
`"epoch"`, so both deaths left nothing to resume from and cost ~41 minutes each.

## F — Numbers that changed once generation was seeded

`generate_lora_voice` never read the seed, so six comparisons were run on
audio where each line was an independent draw of the voice. All are being
re-run rather than defended. Completed so far:

| measurement | contaminated | seeded |
| --- | --- | --- |
| non-prose failures | 21/25, WER 56.65% | **11/25, WER 29.40%** |
| prose failures | 0/25 | **0/25, WER 0.89%** |
| splitting front matter | 7/8 still failed | **8/8 both arms**, split marginally worse |
| bullet-list fix | 0/2 → 3/3 | **3/3, 0 errors** |
| instruct per-line / per-char / none | — | **0.20% / 0.20% / 0.41% WER, 0 failures all arms** |
| within-voice pitch spread | ~103 Hz | **48 Hz** (one adapter) |
| same text, same seed, ×3 | — | **150.048 Hz, identical to 12 dp** |

**The seed bug roughly halved the non-prose failure rate.** The gap survives and
is large — +28.5 WER points at matched length, with symbols already normalised
away — but the number I reported was inflated.

**Splitting is now definitively not the remedy.** 8/8 fail either way. Two of
those segments contained **one item**, could not be split at all, and failed
anyway. That localises the mechanism to the item, not the blob, and is why
`nonprose_mechanism.py` exists.

**Instructions do not change content.** One word of difference across 18
segments in three arms. Whether they change *delivery* is a listening question
the WER harness cannot answer, and the artifact says so rather than implying a
verdict.

**Pitch: the withdrawal stands but for a different reason.** Half the ~103 Hz
instability was the seed bug. The remaining 48 Hz is prosody, and it does not go
away. The scene-aware allocator targeted 17 Hz — a third of what one voice
covers by itself. Not "pitch is unstable" but "voices must be further apart than
the assumed threshold". `pitch_separation.py` measures how much further.

## Two process failures of my own, recorded

**I mutated the live `tts.py` to prove the new seed test could fail,** while an
experiment queue was running against it. The command timed out and left the file
in the bugged state for about two minutes. Restored from git and verified; the
running process had already imported the module, so no output was affected — but
that was luck, not design. Redone on a copy in the scratchpad.

**I collided with my own earlier queue.** A queue launched before the context
compaction was still working through the seeded re-runs. My new one waited for
the wrong process, declared the card free, and started generating alongside it.
Killed mine by PID and chained properly on the driver's PID. Every "noise floor"
in this repo's history has turned out to be another job on the same GPU.

**A claim I had made twice was wrong.** I said the three sibling generation
paths all read the seed. `generate_clone_voice` and `generate_custom_voice`
contain no seed logic at all — they are dispatchers, and the seeding lives in the
`_local_*` implementations one level down. The code was correct; my description
of it was not. The new test asserts the layering so the next reader does not
repeat it, and its first draft failed against correct code for exactly this
reason.
